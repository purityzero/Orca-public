Orca 중앙 오케스트레이션 체제

여러 Unity 프로젝트를 하나의 규칙 베이스로 운용하는 구조를 구축했다. 메인이 명령을 받아 분류하고, 대상 이름으로 에이전트를 배정하고, 작업 결과를 그 이름으로 축적한다 — 다섯 단계가 모두 실제로 동작하며, 그 위에 병렬 실행과 외부 검증을 얹을 설계까지 마쳐둔 상태다.

2026-08-26 · D:\Orca · 에이전트 10 · 누적 기록 140건 · 자동 훅 3

0. Orca가 무엇인가

Orca는 AI 에이전트를 격리해서 돌리고, 그 결과를 비교해 채택하는 도구다. 작업 하나마다 git worktree(같은 저장소의 독립된 작업 폴더)와 브랜치를 만들어 CLI 에이전트를 붙이고, 나온 변경을 diff로 견줘 쓸 것만 합류시킨다. 에이전트를 많이 켜서 빨라지는 도구가 아니라, 여러 시도를 비교 가능한 형태로 바꿔주는 도구다.

이 문서가 다루는 Orca 워크스페이스는 그 위에 얹은 운용 베이스다. 게임 코드는 각 Unity 프로젝트에 있고, 여기엔 코딩 규칙 · 에이전트 정의 · 프로젝트별 작업 기록 · 실행 스크립트만 모았다. 어느 프로젝트에서 세션을 열든 같은 규칙과 같은 에이전트 구성으로 시작하게 만드는 것이 목적이다.

구성역할
규칙 문서 4종코딩 규칙 · 프리팹 규칙 · 에이전트 라우팅 기준 · 행동 지침. 모든 세션이 자동으로 읽는다.
에이전트 정의 10설계 · 구현 · 버그 수정 · QA · 커밋 검토 등 역할별 전문 에이전트. 각자 담당 범위와 모델이 고정.

1. 명령이 지나가는 길 — 5단계 전부 가동 중

단계하는 일구현근거 문서
1 수신공통 베이스 로드 루트 CLAUDE.md가 CODE / PREFAB / AGENT를 함께 로드. 규칙 정본은 워크스페이스에 1부. CLAUDE.md
2 분류축 판정 → 에이전트 선택 설계 / 컨텐츠 / 분량(대·소) / QA(대·소) / 마무리. 축마다 model·effort가 정의에 고정돼 있다. AGENT.MD
3 배정이름 기반 소프트 락 {Project}_{Class}_class로 스폰. 같은 대상이 작업 중이면 자동으로 순위를 미룬다. ParallelWorkContract §11
4 작업소유 파일만 수정 작업 전 대응 md를 먼저 읽는다. 동작이 바뀌는 수정은 work/{날짜}-{주제} 브랜치에서. WorkBranchFlow.MD
5 학습이름 단위 축적 .claude/class/{이름}.md · prefab/{이름}.md로 저장. 요청 없어도 항상 수행된다. CLAUDE.md

3단계 이름에 프로젝트명을 앞에 붙인 건 실측으로 얻은 설계다 — 두 프로젝트가 같은 공용 라이브러리를 써서 클래스명이 겹치는데, 접두사가 이 오인 충돌을 정확히 갈라준다(2026-08-21 레인 3개로 확인).

설계·컨텐츠 병렬 분배설계 완료 수직(도메인) 분할, 메인 선점 후 커밋, 레인별 소유 파일·ID 대역 계약서까지 규격이 서 있다. 레인 2개 실측만 남았다.
외부 모델(Codex) 교차검증확장 예정 붙일 지점이 이미 두 곳 뚫려 있고, 커밋 직전 검토 단계가 그 자리를 먼저 채우고 있다.
간단한 작업은 로컬 LLM확장 예정 모델 계층(opus / sonnet / haiku)이 이미 라우팅에 들어가 있어, 아래 단계를 하나 더 얹는 형태로 확장된다.

3. 이 구조가 선 근거

  • 한 Unity 프로젝트에는 에디터 1 · MCP 브릿지 1 · Play Mode 1 · OS 포커스 1뿐이다. 중앙 체제는 취향이 아니라 이 제약에서 나온 답이다.
  • 그래서 작성은 병렬, 검증은 중앙 집중으로 갈랐다. 에디터 락은 검증 시점에만 걸리므로 작업량의 대부분인 작성 구간은 그대로 병렬로 열린다.
  • 자르는 축을 파일 종류가 아니라 컨텐츠 도메인으로 잡았다. 스키마와 그걸 읽는 코드가 한 레인 안에 통째로 들어온다.
  • 충돌은 경고가 아니라 배분으로 막는다. 공유 등록 파일은 메인이 미리 선점해 커밋한 뒤 계약서에 적어 넘긴다 — 워커 손에 충돌할 파일 자체가 쥐어지지 않는다.
미리 잡아둔 함정 하나: 워크트리 안에서 검증 명령을 부르면 실행 중인 에디터가 열고 있는 원본이 검증된다. 병렬을 켜기 전에 막을 지점으로 문서에 명시해뒀다.

4. 다음 확장

외부 모델 교차검증 — 자리는 이미 준비돼 있다. ① 커밋 직전 게이트: 서브에이전트는 각자 새 컨텍스트라 서로의 실제 시그니처를 못 보고 코드를 쓰는데, 여기에 다른 모델의 독립 판정을 겹치면 같은 맹점을 공유하지 않는다. ② 경쟁 레인의 diff 판독. 두 지점 모두 종료 코드로 판정하는 검증 명령이 함께 서면 곧바로 값어치가 난다.

로컬 LLM 결합 — 토큰 절약 방향은 타당하다. 다만 꽂는 위치는 서브에이전트가 아니라 훅 / CLI 파이프라인이다(이미 세션 시작 · 매 프롬프트 · 세션 종료 세 지점에서 스크립트가 돌고 있어 그대로 확장 가능). 판단이 아닌 생성·변환 구간부터 옮기면 효과가 바로 나온다.

  • 커밋 메시지 · 작업 요약 — 짧고 diff로 즉시 대조되니 가장 먼저 옮길 후보.
  • class / prefab 기록 md 초안 — 포맷이 고정이라 로컬 생성에 적합. 확정만 중앙이 맡는다.
  • 규칙 위반 스캔 — 규칙이 표로 명시돼 있어 정규식·린터와 조합하면 더 싸게 끝난다.
