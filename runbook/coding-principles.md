# C#·Unity 코딩 원칙

C# 코드를 작성·수정하기 전에 `CODE.MD`와 함께 Read로 읽는다. UI·프리팹·동작 변경은 해당 절도 먼저 확인한다.
마지막 적용: 2026-11-05. CLAUDE.md의 코드 전용 상세 규칙을 원문 그대로 옮겼다. 문서·설정에도 적용되는 단순함·최소 침습 원칙은 본문에 남겼다.

## UI·프리팹 규칙

표준 컴포넌트만 상시 규칙으로 둔다. 이것만 어기면 나중에 타입을 통째로 갈아야 한다.

| 용도 | 쓸 것 |
|---|---|
| 텍스트 | `TMPro.TextMeshProUGUI` (legacy `Text` 금지) |
| 클릭 버튼 | `UIButton` (`Button` 상속 확장, 클릭 사운드 키 보유 — 맨 `Button` 금지) |
| 이미지 | `UnityEngine.UI.Image` |
| 목록/스크롤 | `UnityEngine.UI.ScrollRect` |

**프리팹·UI를 만들거나 고치기 전에** `runbook/prefab-ui.md`를 읽는다 — 표준 컴포넌트의 예외,
MCP와 YAML 직접 편집의 선택 기준, 스크롤·풀링·토글 레시피가 거기 있다.
겪은 사고는 `runbook/scene-prefab-edit.md`.
(2026-09-11에 `PREFAB.MD` 상시 주입을 끊고 런북으로 내렸다 — 8K자가 매 세션 들어왔다)

## 검증 전 변경은 기본 브랜치에 올리지 않는다
- 동작이 바뀌는 수정(코드/프리팹/테이블)을 시작하기 전에 `work/{날짜}-{주제}` 작업 브랜치를 만든다. 오타·주석 수준의 수정은 예외.
- 기본 브랜치에는 **사람이 실제로 돌려보고 통과시킨 것만** 합류시킨다. 컴파일 성공은 통과가 아니다 — 지금까지 어긋난 건 대부분 "컴파일은 됐는데 의도대로 안 돌던" 경우였다.
- 한 브랜치엔 한 주제만 담는다. 여러 주제를 섞으면 문제가 난 부분만 되돌릴 수 없다.
- 검증을 못 끝낸 채 세션이 끝나면 브랜치를 지우지 말고 그대로 두고, `.claude/UNFINISHED.md`에 브랜치명을 함께 적는다.
- 절차와 도구(`WorkBranch.cmd`)는 워크스페이스의 `WorkBranchFlow.MD` 참고.

## 착수 전 체크리스트

1. **베이스 클래스를 직접 열어 확인한다** — 커스텀 베이스(풀링 오브젝트, 리스트 아이템 등)는 자체 초기화 훅을
   이미 정의해뒀을 수 있어 `Awake()`/`Start()`를 그대로 쓰면 안 된다. 이름으로 추측하지 않는다.
2. **외부 연동이 필요한 기능은 연동 지점부터 확인한다** — 인터페이스·규격이 이미 있는지 먼저 찾고,
   없으면 로그 스텁 + TODO로 표시해두고 UI·로직 골격부터 완성한다. 상대가 서버든 세이브 시스템이든 같다.
3. **재사용 후보를 먼저 훑는다** — 씬·프리팹에 새 오브젝트를 만들거나 UI를 연결할 때도 같다.
   유사 사례 한두 개만 보고 넘기지 말고 대상 전체의 이름을 훑는다(계층 grep). 일부만 보고 "없다"고 단정해,
   이미 손으로 만들어 화면에 배치돼 있던 진짜 오브젝트를 못 보고 병행 시스템을 새로 만든 사례가 있다.
4. **공급자를 만들면 소비자 전환까지가 한 작업이다** — 기존 소비자를 그대로 두면 새 코드는 검증을 통과하는데
   실제 실행 경로는 한 줄도 안 바뀐다. 완료 조건은 "새 것이 있다"가 아니라 **"옛 경로를 끊어도 프로덕션이 돈다"**.
5. **에셋 참조(GUID 등)는 문맥으로 추측하지 않는다** — 메타·매니페스트를 직접 열어 대조한다.
   필드가 비었거나 이름이 비슷하다고 같은 타입이라 단정해, 여러 세션에 걸쳐 잘못 기록된 사례가 있다.

## 재사용 우선 원칙

- **기존 필드·구조로 표현되면 새로 만들지 않는다.** 새 하위 개념이 기존 enum의 값이나 기존 딕셔너리의 확장으로
  표현되면 별도 데이터 클래스를 만들지 않는다. 단 그 재사용이 나중에 갱신 경로가 뒤섞여 데이터 유실의 원인이
  될 수 있다 — 처음엔 재사용하되 실제로 그 버그가 나면 그때 저장소만 분리한다(공개 API 시그니처는 유지).
- **공용 위젯 베이스가 이미 있는지 상속 관계를 선언부에서 직접 확인한다.** 짐작으로 "완전히 새 클래스가
  필요하다"고 오판해 구조를 손으로 두 번 만들었다 되돌린 사례가 있다.
- **공용 헬퍼를 먼저 검색한다.** 텍스트·스프라이트 세팅, 값 변환(스케일 나누기 등)은 프로젝트 공용 확장
  메서드로 통일하고, 컴포넌트에 직접 대입하는 코드를 반복 작성하지 않는다.
- **공용·제네릭 클래스에 특정 기능 로직을 얹기 전에 전체 사용처를 훑는다.** 빈 확장 포인트에 바로 채우면 구현은
  빠르지만 그 기능과 무관한 사용처까지 추가 필드·매프레임 비용을 함께 떠안는다. 그 기능을 아는 더 좁은
  스코프(실제로 쓰는 호출자 쪽)가 맞는 자리일 수 있다.

## 반복해서 터지는 버그 유형

데이터/설정 레이어(컬럼명 불일치로 조용히 기본값, 초기화 중복 호출로 값이 정확히 N배, 비동기 처리 후 화면 갱신
누락, 리스트 동기화가 merge인지 스냅샷인지, 저장소를 공유한 두 개념이 서로를 침범), 로컬라이제이션 키 관리,
바이너리 자산 병합 — 증상·원인·대응은 `runbook/recurring-bugs.md`에 있다.
**데이터 파일·CSV·텍스트 키·스프레드시트·바이너리 자산을 건드리기 전에 읽는다.**

여기 남기는 상시 규칙은 둘이다.

- **상태를 바꿨으면 그걸 읽는 UI를 전부 갱신한다.** "데이터 갱신"과 "열려 있는 화면 갱신"은 항상 세트다.
  갱신 호출을 헬퍼 하나로 묶어 구조로 막는다.
- **같은 상태를 두 시스템이 각자 들지 않는다 — 소유자는 하나다.** 한쪽에만 변경이 쌓이고 판정은 갱신 안 되는
  쪽을 읽으면 값이 조용히 어긋난다. 정상 경로 테스트로는 안 잡히고 부정 경로(실패·한계 도달)에서만 드러난다.
  두 번째 보유자가 필요해 보이면 위임 읽기로 하나를 정본으로 남긴다.

## 권한 밖 영역과의 경계

상대가 서버든, 다른 팀의 모듈이든, 외부 라이브러리든 같게 적용한다.

- 수정 권한이 없는 영역의 버그는 **원인을 코드 레벨까지 특정한 뒤 수정 지점과 근거를 문서로 전달**하는 것으로
  마무리한다. 직접 고치지 않는다.
- 상대가 아직 안 주는 데이터를 우회 계산으로 메꿀 때는 **"언제 제거해야 하는가"를 주석·문서에 함께 남긴다** —
  나중에 정식 값이 오기 시작하면 그 위에 우회 계산이 이중으로 더해지는 회귀가 된다.
- 상대 영역의 로그를 볼 때는 그쪽 파이프라인이 어디로 출력되는지 먼저 확인한다 —
  내 쪽에서 익숙한 로그 함수가 상대 빌드에선 빈 스텁일 수 있다.

## 단순함을 최우선으로

**문제를 푸는 데 필요한 최소한의 코드만. 추측에 기반한 코드는 금지.**

- 요청받은 것 이상의 기능을 만들지 않는다.
- 한 곳에서만 쓰이는 코드에 추상화를 적용하지 않는다.
- 요청받지 않은 "유연성"이나 "설정 가능성"을 추가하지 않는다.
- 일어날 수 없는 시나리오에 대한 예외 처리를 작성하지 않는다.
- 200줄을 썼는데 50줄로 줄일 수 있다면 다시 작성한다.

자문할 것: "시니어 엔지니어가 보면 과하게 복잡하다고 할까?" 그렇다면 단순화한다.

## 최소 침습 변경

**꼭 필요한 부분만 손댄다. 정리는 내가 어지른 것만 한다.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 포맷을 마음대로 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩토링하지 않는다.
- 내 취향과 달라도 기존 코드 스타일을 따른다.
- 무관한 죽은 코드를 발견하면 알리기만 하고, 지우지 않는다.

내 변경으로 인해 쓸모없어진 코드가 생겼다면:
- **내 변경 때문에** 미사용이 된 using·변수·함수는 제거한다.
- 원래부터 있던 죽은 코드는 요청이 없는 한 건드리지 않는다.

판단 기준: 변경된 모든 줄이 사용자의 요청으로 직접 설명될 수 있어야 한다.

## 클래스 경로 보고
- **클래스를 언급할 때는 항상 열어볼 수 있는 경로를 함께 찍는다** — `절대경로:줄번호` 형식으로 적으면 터미널에서 클릭해 바로 그 줄로 열린다. 클래스 선언부 줄번호를 기본으로 하고, 특정 메서드가 논점이면 그 메서드 줄을 가리킨다. 대응하는 `.claude/class/{클래스명}.md`가 있으면 그 경로도 같이 적는다. 새로 만든 클래스, 수정한 클래스, 설명만 하는 클래스 모두 해당한다.
  - (근거: 보고에 클래스 이름만 적으면 사용자가 파일을 직접 찾아 들어가야 한다 — 경로를 찍어주면 한 번에 열린다. 2026-08-25 사용자 요청)

## 읽기 확인 훅의 범위와 한계

`.claude/hooks/code-rules-gate.js`는 PreToolUse의 Edit·Write·MultiEdit에서 경로가 .cs로 끝나면 작업 폴더 안팎 모두 검사한다. CODE.MD와 이 파일을 성공한 Read의 PostToolUse로 모두 확인해야 같은 session_id의 차단이 해제된다. 정본의 실제 경로를 대조하며 동명 사본·부분 읽기·실패한 읽기는 인정하지 않는다. 전체를 한 번에 Read한다. 두 문서의 표시를 별도 파일로 저장해 병렬 읽기의 상태 덮어쓰기를 피한다.

표시는 `.claude/session-state/{session_id의 SHA-256}/0.json`·`1.json`에 남고 git에서 제외한다. 다른 세션은 다시 읽어야 한다. Bash sed·PowerShell·외부 프로그램의 쓰기는 범위 밖이다. Read 여부를 기록할 뿐 이해 여부를 증명하지 않으며, 같은 세션의 context 압축·재개·문서 갱신 때 재확인은 하지 않는다. `.claude/rules/*.md`의 paths는 Orca 밖 Unity 파일에 자동 적용되지 않으므로 관련 프로젝트 규칙은 직접 읽는다.

훅 입출력은 [Claude Code 공식 훅 참조](https://code.claude.com/docs/en/hooks)의 PreToolUse deny·성공한 PostToolUse 스키마를 따른다. 실제 Claude 세션 통합 시험은 설정 재로딩 후 별도로 한다.
