# Runbook — 반복해서 터지는 버그 유형

데이터 파일·CSV·로컬라이제이션 키·스프레드시트·바이너리 자산을 건드리기 전에 읽는다.
자동 로드하지 않는다(2026-09-11에 `CLAUDE.md`에서 내렸다 — 이 주제를 안 건드리는 세션에도 매번 들어왔다).

`CLAUDE.md`에 상시 규칙으로 남긴 것은 "상태를 바꿨으면 그걸 읽는 UI를 전부 갱신한다"와
"같은 상태의 소유자는 하나다" 두 줄뿐이다. 나머지 세부는 해당 레이어를 만질 때만 필요하므로 여기 있다.

---

## 데이터/설정 레이어 — 반복적으로 터지는 버그 유형

### (1) 데이터 파일 컬럼/키 이름 불일치 — 조용히 기본값으로 귀결
많은 데이터 파싱 유틸리티는 존재하지 않는 컬럼/키를 조회해도 에러 없이 기본값(0, 빈 문자열 등)을 반환한다. 즉 코드가 참조하는 필드명과 실제 데이터 파일의 헤더가 다르면, 컴파일도 되고 실행도 되지만 **항상 기본값**이 되어 이상 동작만 남는다(에러 로그조차 없는 경우가 많다).
- **대응**: 특정 조회 결과가 항상 기본값으로만 나올 때는 계산 로직보다 먼저 "코드가 읽는 필드명 == 데이터 파일의 실제 헤더/키"부터 대조한다. 여러 시스템(클라이언트/서버 등)이 같은 데이터 파일을 서로 다른 파서로 읽는 구조라면, 양쪽 필드명이 어긋나 있을 수 있으므로 양쪽 다 확인한다.

### (2) 초기화 로직 중복 호출 → 값이 정확히 N배
데이터 로딩 파이프라인이 "전체 초기화 시점 1회 호출" + "최초 조회 시점에 아직 준비 안 됐으면 재호출"하는 이중 경로를 갖고 있으면, "준비 완료" 플래그 갱신을 빠뜨린 항목은 데이터가 중복 누적되어 값이 정확히 배수로 튀는 버그가 생긴다.
- **대응 패턴**: 초기화 메서드 시작부에 멱등 가드(`if (준비됨) return; 준비됨 = true;`)를 넣는다. 신규 데이터 로더를 만들 때도 처음부터 이 가드를 기본으로 넣는다.

### (3) 비동기 이벤트 처리 후 화면 갱신 호출 누락
외부 응답이든, 다른 시스템의 콜백이든, 비동기로 들어오는 이벤트 핸들러가 내부 데이터는 정상 갱신하면서 이미 화면에 표시 중인 UI를 다시 그리는 호출을 빼먹는 패턴이 여러 도메인에서 반복해서 발견되는 경향이 있다.
- **대응**: 새 이벤트 핸들러를 작성/수정할 때는 "데이터 갱신" + "관련 화면이 열려 있으면 그 화면도 갱신"을 항상 세트로 체크한다.

### (4) 리스트 동기화가 "부분 갱신(merge)"인지 "전체 스냅샷"인지 반드시 확인
외부에서 오는 리스트가 "활성/점유 항목만 담고, 제거된 항목은 리스트에서 아예 빠지는" 방식이라면, 수신 측이 "리스트에 있는 것만 갱신, 없으면 그대로 둔다"는 merge 방식으로 처리할 경우 제거된 항목이 영영 안 지워진다.
- **대응**: 새 리스트 동기화 로직을 짤 때는 적용 전에 대상 영역 전체를 먼저 비운 뒤 리스트를 재적용하는 "전체 스냅샷" 방식을 기본으로 검토한다. 송신 측이 실제로 스냅샷 방식으로 만드는지 먼저 확인한다.

### (5) 여러 개념이 하나의 저장소를 공유할 때 서로 다른 갱신 경로가 서로를 침범
한 저장소(딕셔너리 등)를 두 가지 다른 개념이 같이 쓰면, 한쪽 개념만 갱신하는 로직이 "전체 클리어 후 자기 개념만 다시 채우는" 방식일 경우 다른 개념의 데이터가 유실된다.
- **대응**: 초기엔 공유해도 되지만(`runbook/coding-principles.md` 「재사용 우선 원칙」 참고), 이런 유실 버그가 실제로 재현되면 저장소를 분리하는 게 근본 해결이다. 임시 백업/복원 패치는 미봉책으로만 취급한다.
- **같은 상태를 두 시스템이 각자 들지 않는다 — 소유자는 하나다.** 한쪽에만 변경이 쌓이고 판정은 갱신 안 되는 쪽을 읽는 "이중 상태"가 되면 값이 조용히 어긋난다. 정상 경로 테스트로는 절대 안 잡히고, 부정 경로(실패·한계 도달)에서만 드러난다. 두 번째 보유자가 필요해 보이면 위임 읽기로 하나를 정본으로 남긴다.

## 로컬라이제이션/텍스트 키 관리

- 새 키를 만들기 전에 **완전히 동일한 문구의 공용 키가 이미 있는지 먼저 검색**한다.
- "키 없는 텍스트 컴포넌트 찾기"는 단순 필드 유무 체크가 아니라 다음 세 가지를 함께 판단해야 한다:
  1. 정적 라벨인가, 아니면 런타임에 코드가 매번 값을 덮어쓰는 표시인가(후자는 키 불필요)
  2. 그 UI 요소가 실제로 살아있는 코드 경로인가, 아니면 비활성 상태로 방치된 leftover 목업인가(죽은 UI는 키 스킵)
  3. 원본(마스터) 데이터와 실제 배포되는 사본(클라이언트/서버 등 여러 곳에 복제되는 경우) 전부를 항상 함께 동기화한다.
- 스프레드시트를 스크립트로 직접 편집할 경우, 수식 셀의 **캐시된 계산 결과값은 저장 시 사라질 수 있음**(수식 자체는 보존되어 다시 열면 재계산됨 — 실데이터 손실은 아니지만, 저장 직후 헤드리스 검증 시 빈 값처럼 보여 착각할 수 있으니 주의).

## 버전 관리 시스템에서 바이너리 자산 병합 주의

- 텍스트 파일(코드, csv 등)의 병합 충돌은 충돌 마커로 명확히 드러나지만, **스프레드시트/이미지 등 바이너리 자산은 병합이 인코딩 손상이나 조용한 데이터 유실로만 나타날 수 있다**(충돌 마커 없음).
- 여러 사람이 "매번 항목만 추가하는" 구조의 파일(enum 정의, 각종 설정 테이블)을 동시에 건드리는 상황에서는, 업데이트/병합 직후 전체 데이터 무결성을 재확인한다 — 병합이 "성공"했다고 표시돼도 실제로는 일부 항목이 사라졌을 수 있다.
- **에셋을 추가하면 그 메타데이터 파일(`.meta` 등)을 반드시 함께 커밋한다.** 빠뜨리면 체크아웃·워크트리마다 엔진이 임의 GUID로 다시 만들어, 같은 경로가 브랜치마다 다른 GUID를 갖는 충돌과 추적 안 되는 잔재가 생긴다.
- **산출물 파일명은 트랙별로 고유하게 정한다.** 여러 작업이 루트에 같은 이름(`report.md` 등)으로 결과를 떨구면 병합 때 add/add 충돌이 난다. `보고서/{주제}-{날짜}.md`처럼 경로에 구분자를 넣는다.
